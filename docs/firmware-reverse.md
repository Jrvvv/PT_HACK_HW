# Способ 2. Извлечение пароля из дампа прошивки

## Идея

Пароль устройства — обычная константа внутри прошивки. Если снять дамп флеш-памяти микроконтроллера и найти в нём место, где происходит сравнение введённого кода с эталоном, пароль можно прочитать напрямую, не вводя на устройстве ни одной цифры. Это статический анализ: устройство при этом даже не обязано быть включено.

## Снятие дампа

Плата CyberSafe построена на микроконтроллере RP2040 (Raspberry Pi Pico) в формате открытой платы, так что доступ к его отладочному USB-интерфейсу не требует пайки. Микроконтроллер переводится в режим загрузчика (замыкание BOOTSEL при подаче питания), после чего он определяется хостом как обычный съёмный накопитель. С помощью штатной утилиты для работы с RP2040 (`picotool`) с этого накопителя снимается полный образ флеш-памяти объёмом 2 МиБ. Чтение флеша в этом режиме не изменяет его содержимое, поэтому дамп можно снимать многократно без риска повредить прошивку.

Результат — файл `pico-flash.bin`, лежащий в `firmware/dumps/`. Рядом сохранён `pico-flash.uf2` (тот же дамп в формате прошивки RP2040) и вывод `picotool` с информацией о чипе.

## Анализ прошивки

Дамп был загружен в Ghidra как образ для архитектуры ARM Cortex-M0, little-endian, с базовым адресом `0x10000000` — именно по этому адресу RP2040 отображает внешнюю флеш-память в адресное пространство исполнения (XIP-режим). После автоматического анализа в прошивке нашлась основная функция инициализации устройства, а внутри неё — вызов функции проверки введённого кода.

Функция проверки пароля расположена по адресу `0x10000ab0`. Она читает состояние энкодера и кнопки, накапливает четыре введённые цифры и построчно сравнивает их с эталонными значениями, лежащими рядом в памяти программы, а не вычисляемыми на лету. При несовпадении она мигает индикаторами ошибки и сбрасывает накопленный ввод, оставаясь в цикле ожидания. При совпадении всех четырёх цифр она возвращает управление вызывающему коду.

Сам пароль лежит открытым текстом в теле прошивки по адресу `0x10005500`: четыре байта со значениями 3, 7, 3, 6. Байтом раньше, по адресу `0x100054ff`, находится служебное значение, с которого начинается эта область данных. Никакого хеширования или шифрования пароль не имеет — сравнение идёт с обычным массивом байт.

## Что происходит после успешной проверки

После того как функция проверки пароля возвращает управление, основной поток инициализации вызывает функцию по адресу `0x10004e64`, которая поднимает USB как накопитель (Mass Storage Class) — именно в этот момент устройство перестаёт быть невидимым для хоста и на компьютере появляется том `PositiveLabs Flash MSC`. До этого момента USB-стек устройства фактически неактивен, поэтому попытки достучаться до накопителя по USB без прохождения проверки бессмысленны — тома физически не существует, пока прошивка сама не решит его создать.

Точка возврата из функции проверки в основной поток находится по адресу `0x100008aa`. Это значит, что достаточно любым способом миновать вызов проверки и передать управление сразу на этот адрес — например, отладочным доступом к ядру через SWD-интерфейс микроконтроллера — чтобы устройство перешло к поднятию USB-накопителя, как будто правильный пароль уже был введён. Такой обход даже не требует знания самого пароля. Мы зафиксировали этот путь статическим анализом, но физически им не воспользовались — в качестве основного доказательства использовали чтение пароля из дампа.

В оперативной памяти устройства проверка также отражается тремя переменными: `0x20002ed0` хранит номер введённой на данный момент цифры, `0x20002ed1` — счётчик подряд введённых верных цифр, `0x20002ed2` — итоговый флаг «пароль принят». Важно, что простая запись единицы в этот флаг сама по себе доступ не открывает: USB-накопитель поднимается только при обычном возврате из функции проверки, а не по факту выставления флага, так что этот путь обхода менее прямой, чем прыжок на `0x100008aa`.

## Восстановление пароля без Ghidra

Раз адрес и структура таблицы с паролем известны, читать её оттуда можно и без интерактивного анализа — просто открыв дамп бинарным образом и взяв четыре байта по нужному смещению. Это реализовано в `tools/pin_model.py`: скрипт открывает `firmware/dumps/pico-flash.bin`, читает четыре байта, начиная со смещения `0x5500` в файле (это тот же адрес `0x10005500` в адресном пространстве флеша, но без базового смещения `0x10000000`), и печатает получившийся пароль. Скрипт содержит самопроверку и на исходном дампе выводит `3736`.

```bash
python3 tools/pin_model.py
```

## Итог

Пароль восстановлен полностью офлайн, без единой попытки ввода на самом устройстве: **3736**. Дополнительно статическим анализом найден путь обхода проверки без знания пароля вообще — через прямой переход выполнения на точку возврата из функции проверки. Подтверждение работоспособности пароля — успешный ввод на стенде и появление на хосте тома `PositiveLabs Flash MSC` (`cafe:4000`) с содержимым, см. `firmware/dumps/usb_token/`.

## Классификация и сложность

Вектор атаки — программный/аппаратный: статический анализ прошивки, извлечённой через отладочный интерфейс микроконтроллера. Сложность эксплуатации средняя: требует снятия дампа флеш-памяти и базовых навыков реверс-инжиниринга ARM-прошивок, но не требует специализированного дорогого оборудования. Метод полностью воспроизводим: любой, кто повторит снятие дампа и откроет его по указанному адресу, получит тот же результат.
